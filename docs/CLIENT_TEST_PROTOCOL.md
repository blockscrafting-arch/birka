# Протокол теста для клиента в production

Документ фиксирует условия и порядок проведения ограниченного прод-теста с участием клиента.

---

## 1. Сценарии для клиента

Используйте [docs/CHECKLIST_VERIFICATION.md](CHECKLIST_VERIFICATION.md) как базовый список сценариев. Для клиента достаточно подмножества:

| № | Сценарий | Ожидание |
|---|----------|----------|
| 1 | Вход в приложение, выбор/создание компании | Компания выбрана, данные загружаются |
| 2 | Клиент → Товары: просмотр, при необходимости создание | Список товаров, создание без ошибок |
| 3 | Клиент → Заявки: создание заявки с одной или несколькими позициями | Заявка создана, отображается в списке |
| 4 | Карточка заявки: позиции, кнопка «Отправить приёмку в Telegram» | Позиции и кнопка работают |
| 5 | Загрузка фото брака (если сценарий включён) | Файл загружается и доступен |
| 6 | Просмотр статусов, остатков (если применимо) | Данные соответствуют ожиданиям |

При необходимости добавьте сценарии по интеграциям WB/Ozon (только с тестовыми ключами) и печати этикеток — по договорённости.

---

## 2. Тестовые данные

- **Компания:** тестовый ИНН или отдельная компания, созданная клиентом в приложении.
- **Товары/заявки:** клиент создаёт минимальный набор сам или вы подготавливаете тестовые данные в выделенной компании.
- **WB/Ozon:** только тестовые API-ключи; не использовать боевые без отдельного согласования.

---

## 3. Окно времени и доступ

- Зафиксируйте даты и время теста (например: «с 10.02 по 14.02, доступ 24/7»).
- URL и способ входа: ссылка на бота/ Mini App, вход через Telegram.
- Ограничение: один аккаунт Telegram (клиента), роль только «клиент» — см. [docs/CLIENT_TEST_ACCESS.md](CLIENT_TEST_ACCESS.md).

---

## 4. Репортинг и контакты

- Укажите контакт для приёма сообщений об ошибках и вопросах (email, Telegram и т.п.).
- Формат обратной связи: описание шага, что ожидалось, что произошло, скриншот при возможности.
- Критичные инциденты: отдельный канал/контакт и срок реакции (например, ответ в течение 4 часов в рабочие дни).

---

## 5. Логирование и ПДн

- На сервере ошибки логируются без записи персональных данных (в логах не должно быть имён, телефонов, полных ИНН в открытом виде — см. правила проекта).
- При необходимости включить более подробное логирование только для тестовой компании/окружения; после теста — отключить.

---

## 6. План отката при критических инцидентах

- **Отзыв доступа:** убрать возможность входа (например, отключить бота для тестового окружения или сменить токен и не передавать новый клиенту) до устранения проблемы.
- **Откат деплоя:** при критической ошибке в релизе — откатиться на предыдущую версию образа/кода по [docs/DEPLOYMENT.md](DEPLOYMENT.md) и перезапустить сервисы.
- **Данные:** решения по удалению или сохранению тестовых данных клиента после теста — по договорённости и политике хранения.

---

После согласования протокола с клиентом и выполнения [docs/PROD_TEST_READINESS.md](PROD_TEST_READINESS.md) доступ на тест можно выдавать.
