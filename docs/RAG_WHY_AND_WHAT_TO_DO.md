# В чём проблема RAG и почему хардкод — не выход

## Что происходит сейчас

1. **Обувь на ВБ → «нет информации»**  
   В DOCX раздел «Обувь» есть, но в ответ попадают другие чанки (или ни один не перекрывает вопрос). В итоге контекст либо пустой, либо не про обувь.

2. **Зеркала → «5 слоёв пузырчатки + пакет/коробка»**  
   Это цитата из раздела **«Автомобильные масла»** в том же DOCX. В контекст подтягивается не тот кусок текста.

3. **Этикетка Ozon → 58×40, 120×75**  
   В наших документах этого нет. Модель отвечает из своих знаний и игнорирует инструкцию «не называй размеры».

4. **Хардкод (расширение запроса ключевыми словами)**  
   Мы подмешиваем к запросу фразы вроде «силикагель 50 мкм» для обуви и «уголки 5-слойный хрупкий груз» для зеркал. Это временно улучшает поиск, но:
   - для каждой новой категории нужно вручную добавлять слова;
   - запрос искажается, логика размазана по коду;
   - при изменении документации ключевые слова могут разъехаться с текстом.

---

## Корневые причины

### 1. Чанки не привязаны к разделам

Сейчас текст режется **по размеру** (например, 1000 символов, overlap 200). Заголовки вроде «Обувь», «Зеркала», «Автомобильные масла» не используются: чанк может содержать полраздела «Зеркала» и полраздела «Сантехника», или полстраницы «Масла» и полстраницы «Шины».  

Эмбеддинг такого чанка — «среднее» по смыслу. Запрос «зеркало на ВБ» по косинусной близости может оказаться ближе к чанку с «маслами» (там тоже пузырчатка, слои, коробка), а не к чанку с «зеркала + уголки + обрешётка».

**Итог:** один только векторный поиск по таким чанкам плохо различает разделы внутри одного длинного документа.

### 2. Нет явной привязки «запрос → раздел»

Мы не определяем, *о чём* спрашивает пользователь (обувь / зеркала / посуда / габариты / Ozon), а сразу ищем по эмбеддингу по всем чанкам. Поэтому:
- при похожих формулировках в разных разделах выигрывает «не тот» кусок;
- короткий запрос «обувь на ВБ» даёт слабый эмбеддинг, и релевантный чанк может не попасть в топ-k.

Хардкод ключевых слов по сути имитирует «мы знаем, что запрос про обувь/зеркала» — но делается это вручную и не через структуру документа.

### 3. Модель не выполняет жёсткий запрет

Фразы в системном промпте вроде «не называй размер этикетки для Ozon» модель иногда игнорирует и всё равно пишет 58×40 и 120×75. Это ограничение именно следования инструкциям, а не RAG.

---

## Что делать по-нормальному (без бесконечного хардкода)

### A. Чанки по разделам, а не только по длине

- При индексации DOCX определять заголовки (например, по стилю или по шаблону «Обувь», «Зеркала», «Посуда») и резать текст **по разделам**.
- Каждый чанк хранить с метаданными: `section=Обувь` или `section=Зеркала`.
- При запросе «обувь на ВБ» сначала фильтровать по `section=Обувь` (или по ключевым словам раздела), потом уже по эмбеддингу внутри этих чанков. Тогда в контекст не попадёт «Автомобильные масла».

Это убирает путаницу между разделами и уменьшает потребность в подборе ключевых слов в запросе.

### B. Явный шаг «намерение / раздел»

- По тексту запроса (или по эмбеддингу запроса к маленькому набору меток) решать: запрос про *обувь* / *зеркала* / *посуду* / *габариты WB* / *Ozon общее* / *этикетка Ozon* и т.д.
- Для «этикетка Ozon» / «размер этикетки Ozon» **вообще не вызывать модель** — отдавать фиксированный ответ: «В загруженной документации нет информации по этому вопросу.» Так мы не зависим от того, слушает ли модель запрет.
- Для обуви/зеркал/посуды — искать только в чанках с соответствующим разделом (см. A).

Тогда логика «что искать» и «что не придумывать» зашита в архитектуру, а не в длинные промпты и не в ручной список слов в запросе.

### C. Гибридный поиск (опционально)

- Помимо векторного поиска, делать простой ключевой поиск (по словам «обувь», «силикагель», «зеркал», «хрупкий» и т.д.) и объединять с векторным (например, по баллам или по объединению топов). Так запрос «обувь на ВБ» гарантированно подтянет чанки, где есть «обувь», даже если эмбеддинг чуть «уплыл».

Это можно вводить постепенно, не отказываясь от текущего векторного поиска.

### D. Ozon: не полагаться на «не пиши размеры»

- Для вопросов про размер этикетки Ozon, красный скотч и т.п. в бэкенде по шаблону/интенту отдавать фиксированный ответ «В загруженной документации нет информации по этому вопросу» и не вызывать LLM. Тогда галлюцинации по этим темам исчезают на уровне продукта, а не промпта.

## Кратко

| Проблема | Причина | Направление решения |
|----------|---------|---------------------|
| Обувь/зеркала — не тот раздел или «нет информации» | Чанки по длине, без привязки к разделам; один векторный поиск по всем чанкам | Чанки по разделам + метаданные; фильтр по разделу/намерению перед поиском |
| Зеркала → текст про масла | Похожие слова в разных разделах, эмбеддинг тянет не тот чанк | Те же разделы + при необходимости гибрид (ключевые слова + вектор) |
| Этикетка Ozon — модель пишет 58×40 | Модель не выполняет жёсткий запрет из промпта | Не вызывать модель для этого интента; фиксированный ответ в бэкенде |
| Бесконечный хардкод ключевых слов | Нет явной структуры «запрос → раздел» и «раздел → чанки» | Вынести «намерение/раздел» и фильтрацию по разделам в архитектуру, ключевые слова использовать системно (метаданные, гибрид), а не точечно в запросе |

Дальше имеет смысл шаг за шагом: сначала разметка чанков по разделам и фильтр по разделу при запросе, затем при необходимости — простой детектор интента для «этикетка Ozon» и фиксированный ответ, потом при желании — гибридный поиск.

---

## Внедрённая схема (RAG по разделам и интент)

Реализовано по плану «RAG по разделам и интент без хардкода»:

- **Чанки с полем `section`:** в таблице `document_chunks` добавлена колонка `section` (String(128), nullable). При индексации DOCX текст режется по разделам (заголовки по стилю или по известным названиям «Обувь», «Зеркала», «Посуда» и т.д.), каждому чанку присваивается ключ раздела (`obuv`, `zerkala`, `posuda` и др.). Для TXT/RTF по имени файла проставляется `wb_common` или `ozon_common`.

- **Детектор интента:** по ключевым словам в сообщении определяется интент (`obuv`, `zerkala`, `posuda`, `gabarity_wb`, `strejch_skotch_wb`, `ozon_etiketka`, `ozon_krasnyj_skotch` или `None`). Модуль `app/services/rag_intent.py`.

- **Фиксированный ответ без LLM:** для интентов `ozon_etiketka` и `ozon_krasnyj_skotch` в `ai.py` до вызова RAG и LLM возвращается ответ «В загруженной документации нет информации по этому вопросу.» и он сохраняется в историю. Галлюцинации по размеру этикетки и красному скотчу исключены на уровне продукта.

- **Поиск с фильтром по разделу:** в `build_rag_context_async` для интентов обувь/зеркала/посуда (WB) добавляется фильтр по `DocumentChunk.section`; для габаритов и стрейч/скотч WB — по `section in (wb_common, NULL)`. Запрос для эмбеддинга — исходное сообщение или нейтральное расширение («Требования упаковки» + сообщение), без подстановки ключевых слов по категориям; функция `_expand_short_query_for_embedding` заменена на `_query_for_embedding` без хардкода.

- **Гибридный поиск:** при включённом `RAG_HYBRID_KEYWORD_BOOST` для интентов obuv/zerkala/posuda после векторной выборки выполняется дополнительный запрос по ключевым словам (ILIKE по `content`: обувь — силикагель, 50 мкм, мешочки и т.д.; зеркала — уголки, пузырчатка, хрупкий; посуда — 2 слоя, пузырчатка). Чанки из ключевого поиска, которых ещё нет в векторной выборке, добавляются к контексту (лимит — `RAG_HYBRID_KEYWORD_CHUNKS_MAX`), общий размер контекста не превышает `RAG_CHUNKS_LIMIT`. Так короткие запросы вроде «обувь вб» стабильнее получают релевантный раздел.

- **Маппинг заголовков DOCX в конфиг:** по умолчанию маппинг «заголовок → section» задаётся в коде (`DOCX_SECTION_HEADING_TO_KEY`). Если в настройках задан `RAG_DOCX_SECTION_HEADINGS_JSON` (строка JSON вида `{"Обувь":"obuv","Зеркала":"zerkala",...}`), при парсинге DOCX используется он — новые разделы можно добавлять без правки кода.

- **Синонимы интентов:** детектор интента распознаёт формулировки вроде «кроссовки вб», «тарелки для вб», «трюмо» (обувь, посуда, зеркала) за счёт дополнительных подстрок в `rag_intent.py`.
