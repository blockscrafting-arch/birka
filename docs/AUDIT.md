# Аудит проекта Бирка (после финальных фиксов)

Дата: 2025-02-27. Обзор безопасности, согласованности логики и оставшихся рисков.

---

## 1. Аутентификация и авторизация

| Аспект | Статус | Комментарий |
|--------|--------|-------------|
| Валидация Telegram initData | OK | HMAC-SHA256 + проверка `auth_date` (replay до 300 с), [security.py](../backend/app/core/security.py). |
| Сессии | OK | Токен в БД, проверка срока. Очистка истёкших при логине. |
| RBAC | OK | `require_roles("admin")` на админке, `require_roles("warehouse", "admin")` на склад и PATCH статуса заявки. Клиент не может менять статусы. |
| Разделение по компаниям | OK | Доступ к заявкам/товарам/отгрузкам проверяется через `Company.user_id == current_user.id` для client; warehouse/admin видят все компании. |

Рекомендация: в production убедиться, что `TELEGRAM_BOT_TOKEN` задан и не утекает в логи (сейчас в логах не подставляется).

## 2. Доступ к данным (IDOR)

- **Orders/Products/Companies:** везде проверка владения компанией или роль warehouse/admin.
- **Shipment/FBO:** привязаны к компании; для клиента проверка `Company.user_id == current_user.id`.
- **Warehouse import-fbo** (`POST /warehouse/orders/{order_id}/import-fbo`): доступ по `get_current_user`; для не-склада проверяется владение компанией заявки — OK.
- **Admin:** только `require_roles("admin")`; удаление документов RAG по `source_file` — точное совпадение в БД, не путь в ФС — OK.

Явных дыр IDOR не выявлено.

---

## 3. Ввод и инъекции

- **SQL:** запросы через SQLAlchemy ORM/select; единственный `text("SELECT 1")` в health — константа. Параметры поиска проходят `escape_ilike` перед подстановкой в `ILIKE` (orders, products, services, admin users, RAG keyword boost) — OK.
- **Файлы:** имена санитизируются `sanitize_filename_for_storage`; загрузки изображений проверяются по сигнатуре (validate_image_signature, safe_open_image). Ограничение размера `MAX_UPLOAD_SIZE_BYTES`.
- **Схемы:** Pydantic для входящих тел; статус заявки — `OrderStatusLiteral` (фиксированный набор).

---

## 4. Секреты и ПДн

- API-ключи WB/Ozon хранятся в БД в зашифрованном виде (Fernet); при отсутствии `ENCRYPTION_KEY` возможен fallback на plaintext — в production обязательно задать ключ.
- В логах по правилу ([logging.py](../backend/app/core/logging.py)) не выводятся telegram_id, токены, пароли; допускаются внутренние id (user_id) для разбора инцидентов. По коду явной подстановки ПДн в логи не найдено.

---

## 5. Rate limiting

- Используется SlowAPI по `get_remote_address`. Для развёртывания за reverse proxy учесть корректное определение IP (X-Forwarded-For и доверие к proxy), иначе лимиты могут применяться по одному IP на всех.
- На критичных эндпоинтах (auth, загрузки, импорт) лимиты заданы (@limiter.limit).

---

## 6. Логика и целостность (после фиксов)

- **Приёмка:** остатки/брак обновляются по дельте; повторная приёмка не раздувает stock/defect.
- **Статусы заявок:** ручное изменение только у warehouse/admin; переходы проверяются через `order_status_flow`; клиент получает 403 на PATCH статуса.
- **Отгрузки WB/Ozon:** при создании заявки на отгрузку вызывается `_validate_marketplace_keys` — проверка наличия и работоспособности ключей.
- **FBO import-barcodes:** нумерация коробов продолжается от max(existing); дубликаты баркодов в одном запросе отбрасываются.

## 7. Рекомендации

1. **Production:** задать `ENCRYPTION_KEY` и не использовать пустой; проверить, что CORS_ORIGINS — явный список, не `*`.
2. **Proxy:** при наличии nginx/другого proxy настроить передачу реального IP и при необходимости — лимитер по заголовку (если SlowAPI будет поддерживать).
3. **Тесты:** один тест FBO был скорректирован под фактическое поведение (Ozon draft без ключей — 200); остальные 42 целевых теста проходят.
4. **Документация:** BACKEND.md приведён в соответствие с запуском автозакрытия отгрузок через Celery Beat и операционным контуром (API / worker / beat).
