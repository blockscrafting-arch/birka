# План: ТОП-3 по аудиту (безопасность, UX, бренд)

**Источник:** `docs/AUDIT_DEEP_REVIEW.md` (оценка готовности 76%).  
**Дата плана:** 2026-02-09.

---

## 🎯 Цель этапа

1. **Безопасность:** Исключить загрузку в S3 файлов, не являющихся изображениями (проверка по magic bytes, а не только по Content-Type).
2. **UX:** Дать пользователю явную обратную связь при ошибке входа через Telegram (сообщение + возможность повтора).
3. **Бренд:** Привести сообщения API к единому русскому языку (404/403 и ключевые бизнес-ошибки).

## 📋 Пошаговый план (Execution Checklist)

### Блок 1: Magic bytes для загружаемых изображений

- [ ] **Step 1.1: Добавить зависимость `filetype`**
  - *Context:* Нужна проверка типа файла по magic bytes (без libmagic). Библиотека `filetype` (h2non) принимает `bytes`/`bytearray`, возвращает `kind.mime` / `kind.extension` или `None`.
  - *Files:* `backend/requirements.txt` (или pyproject.toml, если используется).
  - *Validation:* `pip show filetype` в venv проекта; при необходимости `python -c "import filetype; print(filetype.guess(bytes([0x89,0x50,0x4E,0x47])))"` → ожидаем тип PNG.

- [ ] **Step 1.2: Ввести утилиту проверки типа изображения**
  - *Context:* Единое место проверки: по первым байтам определить тип; разрешить только изображения (например, image/jpeg, image/png, image/gif, image/webp). При несоответствии — понятная ошибка.
  - *Files:* `backend/app/core/utils.py` (или отдельный модуль, например `backend/app/core/file_validation.py`).
  - *Validation:* Unit-тест или ручной вызов: передать bytes PNG/JPEG — OK; передать bytes PDF или случайные — ошибка/False. *Context7 Check:* Сигнатура `filetype.guess(buf)` — принимает path или bytes (подтверждено веб-поиском и докой).

- [ ] **Step 1.3: Встроить проверку magic bytes в загрузку фото товара**
  - *Context:* После проверки прав и лимита размера, прочитать содержимое файла, вызвать проверку по magic bytes; при неудаче — `HTTPException(400, detail="Неподдерживаемый тип файла")`. Затем существующая логика (PIL, S3).
  - *Files:* `backend/app/api/v1/routes/products.py` (эндпоинт загрузки фото товара).
  - *Validation:* curl/Postman: отправить файл с Content-Type: image/png, но телом PDF — ответ 400 с текстом «Неподдерживаемый тип файла». Отправить реальный PNG — 200.

- [ ] **Step 1.4: Встроить проверку magic bytes в загрузку фото заказа**
  - *Context:* Аналогично Step 1.3 для загрузки фото к заказу.
  - *Files:* `backend/app/api/v1/routes/orders.py` (эндпоинт загрузки фото заказа).
  - *Validation:* Аналогично: подмена тела при image/* → 400; реальное изображение → успех.

### Блок 2: Обратная связь при ошибке авторизации в App

- [ ] **Step 2.1: Состояние ошибки авторизации и показ сообщения**
  - *Context:* При неудачном `POST /auth/telegram` пользователь должен видеть короткое сообщение («Не удалось войти» / «Ошибка входа»), а не пустой интерфейс. Использовать `useState` для `authError` (например, строка или null), выставлять в `.catch()`.
  - *Files:* `frontend/src/App.tsx`.
  - *Validation:* В DevTools временно подменить ответ auth на 401 или отключить бэкенд — после загрузки приложения должен отображаться блок с текстом ошибки входа.

- [ ] **Step 2.2: Кнопка «Повторить» при ошибке входа**
  - *Context:* Дать пользователю возможность повторить попытку входа без перезагрузки страницы (например, кнопка «Повторить», по нажатию сброс `authError`, повторный вызов API или сброс `ready` и повторный эффект инициализации).
  - *Files:* `frontend/src/App.tsx`.
  - *Validation:* Вручную: вызвать ошибку входа → нажать «Повторить» → убедиться, что снова идёт запрос к `/auth/telegram` и при успехе сессия появляется.

## ⚠️ Риски и нюансы

| Риск | Митигация |
|------|-----------|
| **filetype не распознаёт какой-то допустимый формат** | Явно разрешать только список MIME (jpeg, png, gif, webp). Остальные image/* отклонять с «Неподдерживаемый тип файла». |
| **Двойное чтение файла** | Текущий поток уже читает файл в память для PIL. Проверку magic bytes делать по тем же данным (прочитать один раз → filetype.guess(data) → при успехе передать в PIL). Не читать файл дважды с диска. |
| **Большие файлы в памяти** | Лимит размера уже проверяется до чтения; для изображений достаточно прочитать первые ~261 байт для filetype, но для PIL нужен весь файл — оставить текущую схему (лимит + один read). |
| **Ошибка входа при отсутствии initData** | Сейчас при отсутствии initData приложение просто помечает ready и не показывает ошибку. Решить: не считать это «ошибкой входа» или показывать отдельное сообщение («Откройте приложение из Telegram»). В плане — показывать ошибку только при наличии initData и неуспешном ответе API. |
| **Регрессия тестов** | Тесты, проверяющие точный текст `detail`, нужно обновить на русские формулировки. |
| **Логи и мониторинг** | Не логировать тело запроса и пользовательский ввод (уже отмечено в аудите); при переводе сообщений не менять коды ответов, только текст. |
